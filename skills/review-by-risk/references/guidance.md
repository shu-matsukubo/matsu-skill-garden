# 判断と手順

## 検証強度

- 重要度、影響範囲、失敗時の損失、検出価値、時間、認知資源から強度を決める。
- 開発用の仕組みでも、破壊や漏えいにつながる操作は高リスクとして扱う。
- 高コストな品質保証の必要性は、入口で判断する。
- 品質保証付きWorkflowを選んだら、工程ごとに同じ人間確認を繰り返さない。
- このSkillの利用だけを理由に、承認や独立レビューを一律に追加しない。

## 判定の分担

| 判定 | 担当 |
| --- | --- |
| 決定的に再現できる不具合 | 静的検査・テスト |
| 推論が必要な整合性 | AI |
| 仕様の意図・期待結果 | 責任を持つ人 |

- 重要なセキュリティ領域は、複数の手段で確認する。
- 分担しても、検証責任は維持する。
- AI開発基盤は、型検査・Lint・Formatter・構成検査を先に選ぶ。
- 次に、責務、配置、参照関係で判断を助ける。
- 仕様の解釈などは、自然言語の判断基準で補う。
- 既存ツールを優先し、独自検査やGit操作ラッパーは不足を埋める場合に絞る。

## 独立レビュー

- 作者は、先に自分で確認できる破損・不足を直す。
- 別の実行主体は、作者が見落としやすい要求・scope・品質を調べる。
- 読み取り専用レビューでは、行動指示、環境が防ぐ書き込み、事後の差分検出を区別する。
- 標準のサブエージェントと利用可能な権限制御を優先する。
- 専用Agentや隔離が任意なら、必要な保証を満たす範囲で続ける。
- 厳格な隔離が必須で確保できなければ、保留して未実施を示す。

## ゲートの改善

- 追加ゲートは、既存の保証で検出できない失敗と増分価値から選ぶ。
- 指摘がなくなるまで無条件に反復しない。
- 少数試行は傾向として示し、正式リリースでは強度を改めて判断する。
- CIを、変更した責務と影響範囲へ対応付ける。
- 許容リスク内でのリリースを前提に、実利用の問題と見逃しの理由を評価する。
- 利用者数や利用方法が変わったら、リスクと強度を見直す。
- AIレビューの指摘がなくなったことを、不具合がない証明にしない。

## PR検証の設計

- 最新headに対する必須CIの照合方法を決める。
- 失敗時の修正範囲、待機と試行の上限、人への引き継ぎを決める。
- PRの作成・更新・公開・マージの実行手順は、対象ワークスペースに置く。
